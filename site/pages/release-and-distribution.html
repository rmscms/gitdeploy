Release

Release and Distribution Guide

This page explains release versioning, Git tags, packaging choices, and what each artifact type means for end users.

Versioning Process

Before Tagging

  • Update version in project file (Version, AssemblyVersion, FileVersion).
  • Run compile/build checks and validate critical pages.
  • Commit all release-scoped changes to main.

Tag and Push

  • Create annotated tag (example: v1.2.4).
  • Push main and release tag to origin.
  • Generate final ZIP artifact in releases/.

Artifact Types

Self-Contained Package

Includes .NET runtime files. Larger ZIP, but no runtime installation needed on target machines.

  • Typical size: tens of MB.
  • Best for isolated environments and non-technical operators.
  • Command: dotnet publish -c Release -r win-x64 --self-contained true

Framework-Dependent Package

Requires matching .NET runtime on target machines. Smaller ZIP and faster transfer.

  • Typical size: single-digit MB to low teens.
  • Best for managed developer environments.
  • Command: dotnet publish -c Release -r win-x64 --self-contained false

Release Checklist

  • Confirm branch is clean and synced with origin.
  • Compile the solution and validate high-risk workflows.
  • Commit with release-focused message.
  • Tag the release and push tag + branch.
  • Create ZIP in releases/ with predictable naming.
  • Publish changelog highlights for operators and developers.
Naming convention: keep artifact names deterministic, such as GitDeployPro-vX.Y.Z-win-x64.zip.
